# Decisions log

Short records of decisions that shape the project. Newest at the bottom. Status: **accepted**, **provisional** (revisit soon), or **superseded**.

---

### D-001 — Name: Emaki (accepted)
*Emaki* (絵巻, "picture scroll", pronounced eh-MAH-kee) are Japanese illustrated handscrolls from the 12th century onward: pictures and text read scene by scene as the scroll unrolls. They are an ancestor of the visual novel, a story told through pictures and words, one scene at a time.
Short, meaningful, rarely used in software, and works as a CLI name (`emaki`), a package scope (`@emaki/*`) and a "Made with Emaki" credit. Chosen over Lantern (too generic), Benshi, Kamishibai, Limn and Quire. Formal trademark checks are deferred.

### D-002 — License: MIT, no royalty on the core (accepted)
The engine, editor and exports are free forever. Ren'Py is free and MIT, so any fee on the core would be a reason not to switch, and royalties can't be enforced on OSI-licensed code anyway. If paid offerings ever exist, they will be optional services around the engine (for example console-port support or cloud builds), never a tax on the core or on games made with it.

### D-003 — TypeScript for everything in v0 (accepted)
Biggest contributor pool, the editor is a web-UI problem, and web/mobile become native targets instead of ports (Ren'Py's weakest areas). Consoles later via a native player that implements the compiled format (D-005).

### D-004 — No build step: Node type stripping + `.ts` imports (accepted)
Node ≥22.18 runs `.ts` directly; Vite and Vitest handle the same files. Packages export `src/index.ts`. Constraint: erasable TypeScript only (no enums/parameter properties/namespaces). Revisit if we publish to npm (we'd add a build that emits `.js` + `.d.ts`).

### D-005 — Compile to a portable JSON instruction list (accepted)
Source `.vn` → AST → flat instruction array with resolved jump targets + expression trees as JSON. Any runtime (TS today, Rust/C++ for consoles later) implements ~14 opcodes and a tiny expression evaluator. Spec: docs/story-format.md. Versioned by `FORMAT_VERSION`.

### D-006 — Screenplay-style, indentation-based syntax close to Ren'Py (accepted)
Writers already know Ren'Py; it makes the planned Ren'Py importer easy. Differences from Ren'Py, on purpose:
- Dialogue text is **unquoted** (`mira: Hello.`), like a screenplay. Quotes are optional.
- `set x += 1` instead of `$ x += 1`: no embedded Python; a small sandboxed expression language (`and`/`or`/`not`).
- Variables must be declared (`var trust = 0`) so typos are caught at compile time.
- Reaching the end of a label **returns** (or ends the story) instead of falling through into the next label. Fall-through is a classic Ren'Py bug source.

### D-007 — Sandboxed expression language, not JavaScript (accepted)
Portable to native runtimes, can't touch the host, statically analysable (free variables → typo detection, reachability). Escape hatch for power users will be a plugin API, not inline code.

### D-008 — Stable line ids = label + hash(speaker|text) (provisional)
Used for localization keys, live-reload resume, and (later) save robustness. Editing a line changes its id, which is correct for translation ("this line changed, re-translate"). Duplicates in the same label get a `.2` suffix. Revisit: optional explicit ids (`#id`) for lines writers want to pin.

### D-009 — Runtime is a headless VM producing Steps (effects + one blocking event) (accepted)
DOM-free so it's testable in Node and reusable by any renderer. Rollback = snapshot per blocking event (bounded, 500). Saves = full state snapshot + story hash. Live-reload `resume()` relocates by line id when the story changed.

### D-010 — DOM/CSS renderer first, WebGL later (accepted)
v0 player is plain DOM: accessible, crisp text, tiny (≈13 KB gzipped incl. engine). The Effect/Block contract lets a PixiJS/WebGL renderer drop in later for shaders/particles without touching the VM.

### D-011 — Sprite attributes replace, they don't merge (provisional)
`show mira smile` then `mira sad: ...` → attrs become `[sad]`. Simpler than Ren'Py's attribute merging; revisit when layered sprites (outfit + expression) arrive.

### D-012 — Comments are full-line `#` only (accepted)
Inline comments would conflict with dialogue text containing `#` ("mira: Room #4"), so a comment is always a whole line. Comments are preserved by the formatter; see D-015.

### D-013 — The story map is a dev-only tool (accepted)
The flowchart of scenes, play-from-here and live variable editing exist to help writers test routes. They are loaded lazily on the dev server only: the Vite plugin emits the story graph only when serving, and the map module sits behind `import.meta.env.DEV`, so published games never ship a spoiler map of their own routes or the extra code. A player-facing route chart (as some VNs offer after completion) would be a separate, opt-in feature.

### D-014 — Flowchart layout is home-grown, not a dependency (accepted)
A small Sugiyama-style layered layout (back-edge detection, longest-path layering, barycenter ordering) in `player-web/src/map/layout.ts`. Story graphs are small (tens to a few hundred labels), so a ~200-line pure function beats pulling in dagre/elkjs. It is DOM-free and tested, so the future editor can reuse it. Revisit if large stories need better edge routing.

### D-015 — Comments and blank lines live in the AST as "leading trivia" (accepted)
Every node (declaration, label, statement, menu choice, elif/else branch) can carry `leading: string[]`: the comments ("# ...") and blank lines ("") written directly above it. Comments after the last line go in `Program.trailing`. The printer writes them back, so the formatter and the future visual editor never lose a writer's notes.
The AST is kept canonical so `parse(print(ast))` equals `ast`: consecutive blank lines collapse to one, and a blank line is dropped where the printer always puts one anyway (start of a block, before each label, before the first item of each declaration group). Canonical files round-trip byte for byte (`print(parse(text)) === text`), and CI checks the demo with `emaki fmt --check`.
A comment attaches to the next line regardless of its indentation, so a note left at the end of a block moves to the line after the block when formatted. Simple and predictable; revisit if writers find it surprising.

### D-016 — Text styling is Markdown-like and compiled into spans (accepted)
`*italic*`, `**bold**` and `[color=...]...[/color]`, because writers already know Markdown, and square-bracket tags can't clash with `{variable}` interpolation. Markup is parsed at compile time: instructions keep plain `text` and gain optional `spans`, so the format change is additive (`FORMAT_VERSION` stays 1) and a variable's value can never be mistaken for markup. Unbalanced markers are errors, not guesses. Quoted strings keep unknown backslash escapes such as `\*`, so escaping works the same quoted or unquoted.

### D-017 — Player settings are per game, validated, and applied through CSS variables (accepted)
Text speed, auto-advance wait, volumes, text size, text box opacity, font and animations. Stored in localStorage per game title; every value is clamped or defaulted on load, so a bad stored value can't break the player. Visuals are driven by CSS variables and classes on the stage, so themes can restyle without touching code. "Animations: follow my device" is the default, respecting `prefers-reduced-motion`.

### D-018 — The stage adapts to its host: 16:9 letterbox when wide, full-screen portrait when tall (accepted)
The player marks the element it mounts into as a CSS size container and lays out from the host's shape, not the window's, so the dev story map, an embed or a phone all behave the same. Hosts taller than 4:5 get the portrait layout: the stage fills the host, backgrounds crop to the centre, characters stand above a full-width textbox, and the quick menu sits below it in one row. Everything inside sizes off one unit, `--u` (1% of stage height in landscape; tied to the width in portrait), and sprite positions are CSS variables (`--pos-left/center/right`), so a theme can retune either layout without code. Games are still authored for 16:9; per-image focal points for portrait cropping can come later.

### D-019 — Preloading is a static lookahead in the runtime; the player waits briefly, never forever (accepted)
`Runner.upcomingImages()` walks the compiled code from the current position without running it: every branch of conditions and menus, into calls and back out, up to a few lines/menus away (and a hard cap on instructions visited). That keeps it deterministic and testable without a browser, and any future runtime gets the same behaviour. The web player keeps the results loaded and decoded (a small most-recently-used cache) and, when a step changes the picture, holds that step for at most 1.5 s until its images are ready, so nothing fades in half-loaded. A slow or missing file never blocks the story, and skip mode doesn't wait at all.

### D-020 — Editor support lives in an editor-agnostic module; the VS Code extension is a thin, bundled adapter (accepted)
`packages/language` (originally `packages/vscode/src/language.ts`) implements problems, symbols, definition, references, hover, completion and formatting as plain functions over text and 0-based positions, built on the real compiler, so the editor always agrees with `emaki check`. It has no VS Code imports, is unit-tested, and can back a language server or the web editor later. `extension.ts` only translates to the VS Code API. This is the one package with a build step: VS Code can't run TypeScript, so esbuild bundles the extension and the compiler into a single file that needs nothing installed. The TextMate grammar is tested with `vscode-textmate`, the engine VS Code itself uses. Not yet on the Marketplace.

### D-021 — Line previews rebuild the scene by replaying the label, not by running the story (accepted)
`Runner.startAtLine(n)` starts at the first instruction on or after line `n`. To avoid opening on a black screen, it replays the `scene`/`show`/`hide`/music statements from the top of that label down to the line, ignoring conditions and menus (when two branches both change the picture, the later one wins). Running the story from the start instead would need a path of choices to reach the line, which may not exist for the variables being tested. The approximation is predictable, covers the usual case (a label sets its scene near its top), and the writer can set variables in the link (`?line=52&trust=2`). Previews are dev-only: a published build ignores `?line=`. After a live reload the player resumes where it was, unless the address changed, so following a new preview link always wins.

### D-022 — Accessibility fonts are bundled with every game, loaded on demand (accepted)
Players can switch story text to Atkinson Hyperlegible (designed for low-vision readers) or OpenDyslexic. Both are SIL Open Font License, so any game, free or commercial, can ship them; they come from `@fontsource` packages and are bundled into the build rather than fetched from a font CDN, so games work offline and don't contact third parties. Only `@font-face` rules are loaded up front: a font's files download the first time a player picks it, so a game that nobody switches costs nothing extra. OpenDyslexic's large letters are evened out with `font-size-adjust`.

### D-023 — Demo audio is downloaded CC0, not generated; the player keeps plain HTML audio for now (accepted)
Games bring their own audio; the demo only needs enough to exercise the audio path and sound decent. We use CC0 recordings from OpenGameArt (credited anyway in `CREDITS.md`, shipped with the build) rather than synthesising placeholder tracks, which would be code nobody needs. CC-BY assets were passed over so the demo carries no attribution obligations. Files are MP3 because every browser plays it. Playback stays on `HTMLAudioElement`: `fade` now works for `play` and `stop` (a new track crossfades over the old one), and sound effects are not played when skipping, rolling back or loading, so they don't fire in bursts. Known limit: MP3 loops can have a tiny gap at the loop point; gapless looping through Web Audio is on the roadmap, along with an ambience channel that can play under music.

### D-024 — Reduced motion doesn't change text speed (accepted, amends D-017)
Previously "reduced motion" also made text appear instantly. That surprised players: Windows reports reduced motion whenever "Animation effects" is off, a common setting, so their text never typed out, even though Text speed was set. Reduced motion is about movement (fades, slides, bouncing indicators), and letters appearing in place isn't movement. Typing is now controlled only by Text speed, which has its own Instant option. Reduced motion still makes transitions instant and stops the next-line indicator from bouncing.

### D-025 — The editor is a local web app over the game folder, built from the engine's own parts (accepted)
`npm run edit` serves the editor with Vite, the same way `npm run dev` serves the game. A small plugin gives the page one API, read and save `story.vn`. The text on disk stays the single source of truth, so writers can use the editor, VS Code and git on the same file at once. The editor reuses everything it can. The script pane is CodeMirror 6 driven by `@emaki/language` (moved out of the VS Code extension for this), so both editors report the same problems. The game pane is the real web player. The flowchart uses the story map's layout. As you type, the script is recompiled and `Player.reload()` swaps in the new story at the same line through `Runner.resume()`, the same path live reload uses, so music and the scene carry on.
Saving is automatic, a moment after typing stops. Every save says which version of the file it was based on (a hash). If the file changed on disk in the meantime, the save is refused and the writer chooses which version to keep. A change on disk is loaded silently only when the editor has no unsaved edits. Writes go to a temporary file that is then renamed, and keep the file's line endings. The API only answers requests from the editor's own page, so another website open in the browser can't rewrite the script. A desktop wrapper (needed anyway for exports, Milestone 3) can reuse all of this. Revisit: editing several `.vn` files once stories can span files.

### D-026 — Visual edits are tree edits printed back to text; the script stays the source of truth (accepted)
The flowchart and the asset browser never keep their own copy of the story. Each action (add, rename, delete or connect a scene, declare or drop an asset) is a pure function in `@emaki/language/edits`: it parses the script, changes the syntax tree and prints it with the printer. That gives canonical text with every comment kept (D-015). The editor applies the result as an ordinary edit, so it is saved, played and undone (Ctrl+Z) exactly like typing. A script with syntax errors is never edited, because printing an incomplete tree could drop lines; the writer is told to fix the error first. Because the printer is canonical, the first visual edit to an unformatted script also tidies its layout (the same as `emaki fmt`).
The edits are deliberately conservative. Deleting a scene is refused while anything still leads to it, and so is deleting the start scene. Connecting a scene appends a `jump` if it just ends. If it already jumps, the jump becomes a `menu` with a placeholder choice for each destination ("(Choice) Kitchen talk"), and a scene that ends in a menu gets one more choice. A scene that `return`s is left alone. The rules for anything subtler are better expressed in text, and the flowchart shows exactly where (click an arrow to see its line).

### D-027 — Assets dropped into the editor are copied in, never overwritten, and named from the file (accepted)
Files dropped from the computer go to `assets/images/` or `assets/audio/` under a cleaned-up name. If a file with that name exists, the same bytes reuse it and different bytes get a numbered copy, so nothing a writer made is ever replaced. Declarations are named from the file name: `Cliff Road (dusk).png` becomes `cliff_road_dusk`, a `bg_` prefix is dropped, and a file starting with a character's id (`mira_smile.png`) becomes that character's sprite, `mira smile`. Dropping an asset inside a scene also adds the statement: `scene` for a single name, `show` for a sprite, `play music` (or `play sound` for files in an `sfx`/`sound` folder). Uploads are accepted only from the editor's own page and only for image and audio types.

### D-028 — Translations are catalogs keyed by line id, in PO or CSV; the runtime swaps text by id (accepted)
A translation is a file per language in the game's `lang/` folder: `fr.po` for translation tools (Poedit, Weblate and Crowdin all read gettext PO), or `fr.csv` for spreadsheets. Each entry is keyed by the line's stable id (D-008), which goes in `msgctxt`, so identical sentences in different scenes can be translated differently. The compiler lists every string a player reads (lines, choices, character names, the title, achievements) with its id and raw source text, markup included, so the exporter and the runtime can't disagree about ids. The player's own buttons (`ui.*`) go into the same file, so a translated game is translated all the way through, not just its story.
`emaki strings --lang fr` creates or updates a catalog. Existing translations are kept. Because a line's id hashes its text, editing a line gives it a new id; the update then offers the closest old translation from the same scene (word-level similarity of 0.5 or more) as a *review* entry (fuzzy in PO). Translations for deleted lines are kept as obsolete, so no translator's work disappears. The game uses only reviewed (`ok`) entries and shows the original for anything else. Compiling a translation checks its markup, and refuses `{variables}` that the original line doesn't use, because a typo there would show players "{nmae}".
At runtime `Runner.setTranslation()` swaps text by id when blocks are built. Switching language mid-scene redraws the current line, and rollback, loads and the history log follow the new language. The player picks a language from Settings, which defaults to matching the device's languages (an exact match first, then the base language, so `pt-BR` falls back to `pt`), and sets `lang` and `dir` (right-to-left) on the stage. Plural forms are not supported yet; PO entries that use them are reported and ignored.

### D-029 — Desktop export uses Electron, not Tauri (accepted)
Tauri makes much smaller apps (a few MB instead of about 300 MB unpacked), but it renders with each system's own web view: WebView2 on Windows, WebKit on macOS and WebKitGTK on Linux, which differ in audio, fonts and CSS container queries (the player relies on these, D-018). It also needs a Rust toolchain on every developer's machine. Electron ships one known Chromium everywhere, so a game looks and sounds the same as in the dev server, and it exports with nothing but npm: `@electron/packager` downloads the right Electron for each target, so one machine can build for Windows, macOS and Linux. The shell (`packages/desktop/app`) is small, plain JavaScript shipped as-is. It serves the game over a private `app://` scheme, because `file://` can't load module scripts. Pages get no Node access (context isolation, sandbox), and the only bridge is the `EmakiHost` interface. Chromium's interface translations, which a game never shows, are trimmed to English plus the game's languages (about 45 MB saved). Revisit Tauri if download size becomes the main complaint, once system web views have caught up.

### D-030 — Steam support is optional, through steamworks.js, behind the host bridge (accepted)
A game gets Steam by adding `steam_app_id` to its header. Only then does the desktop export include `steamworks.js` (MIT, prebuilt for each platform, with Steam's own library), unpacked outside the asar archive so it can load. The shell starts Steam before the window opens (needed for the overlay), and maps `achieve <id>` to the Steam achievement with the same id. If Steam is unavailable, the game runs without it. Achievements themselves are part of the language (`achievement id "Name"` declares one, `achieve id` awards it), so the compiler catches typos, names are translatable, and every platform behaves sensibly: Steam's popup on Steam, an in-game notice and local record everywhere else. The player reaches platform features only through `window.emakiHost` (quit, full screen, achievements, back button), which each shell provides as far as it can, so the same web build runs everywhere. The compiled format gains an optional `achievements` table and an `achieve` op; like styled spans (D-016) this is an addition, so `FORMAT_VERSION` stays 1 until the format is first published.

### D-031 — Phone export generates a Capacitor project once and only syncs it afterwards (accepted)
`emaki export android|ios` writes a Capacitor project to `<game>/export/mobile`. The first export runs `npm install` and `cap add`; later exports copy the new web build in with `cap sync`. Native changes made in Android Studio or Xcode (signing, icons, store settings, orientation) therefore survive re-exports, and the generated projects are ordinary ones that any Capacitor guide applies to. The engine itself depends on no Capacitor package: the project pins compatible versions, and the player finds the App and StatusBar plugins on `window.Capacitor` at run time (for the back button, quitting on Android, and a hidden status bar). An APK is built only when the Android SDK is found. Otherwise, and always for iOS off a Mac, the export prepares the project and says exactly what to do next. Signing for the stores stays in the native tools, where store requirements change.

### D-032 — Skip stops at unread text by default (accepted)
The player records which lines have been read, by line id (D-008), across every playthrough on the device, and skip stops at the first line not read before. That is what makes replaying a branching story for its other routes bearable, and what players of the genre expect. Because a line's id hashes its text, a line the writer changes counts as unread again, which is right: it is new text. Settings has "Skip: Text you have read / All text" for players (and writers testing) who want the old behaviour. The record is one JSON list per game, written in batches so skipping thousands of lines doesn't write to storage on every line.

### D-033 — The title screen is customized in three layers (accepted)
Header keys cover what most games need (`title_image`, `title_music`, `title_logo`, `title_layout`, `title_buttons`). A `theme.css` in the game folder restyles anything, against a documented, stable set of class names (docs/theming.md). For full control, a label named `title` *is* the title screen: it plays like any scene, and its `menu:` becomes the title menu, followed by the built-in Load, Settings and Quit. This keeps title screens in the story language rather than a separate screen language: conditions, `global var` unlocks, translations and the editor all work on them unchanged. A choice on the title starts a new game from that choice, with rollback cleared so going back can't return into the title. `title` is never chosen as the start label by default and always counts as reachable.

### D-034 — A story can span many files; story.vn is the main one (accepted)
Every `.vn` file in the game folder (except in assets, lang, dist, export and tools) is part of the story, with one shared namespace: no `include` lines to keep in order, and scenes can move between files freely, because line ids depend on the label and text, not the file. Only story.vn has a header. The compiler parses each file, tags every location with its file, and compiles the merged program, so diagnostics, source references in the compiled story, the story map, preview links (`&file=`) and translation references all name the file. Locations in story.vn carry no file, which keeps single-file stories and their compiled output exactly as before. The editor and VS Code analyse each file with the others' current (unsaved) text, and the flowchart's scene edits work across files (renaming updates jumps everywhere).

### D-035 — Engine features come from real games (process)
Porting a complete existing visual novel (34 scripts, about 4,600 lines, 1,700 voice files, three endings) was used to find what Emaki couldn't yet express. The conversion script stayed outside the repository; only general features the port proved necessary were added: `aspect`, real sound and voice channels, percentage positions, `global var`, `narration: plain`, read-text skip, the scripted title screen and multi-file stories. New features should keep coming from games like this rather than from feature lists.

### D-036 — NVL mode is part of the story state, and pages turn over by themselves (accepted)
`nvl on` switches to pages of full-screen text, `nvl off` back to the text box, and `nvl clear` starts a new page; `nvl: on` in the header starts a story that way. The lines on the current page are kept in the runner's state (at most 40; a page shows fewer), so rollback, loading and switching language redraw exactly what was on screen. The player lays a page out from its first line and starts a fresh page when the next line wouldn't fit, the way a printed or DS novel does, so writers rarely need `nvl clear`; a new `scene` also starts a new page. The typewriter writes into whichever element shows the current line, so typing, auto, skip and voices behave the same in both modes.

### D-037 — Extras come from declarations, and progress is per device (accepted)
A gallery image is an ordinary image declared with `gallery`; an ending is declared with `ending id "Name"` and reached with `end id`. Keeping both in the script means the compiler checks them (an `end` with a misspelled ending is an error), their names are translatable, and the Extras screen needs no separate configuration. The player records gallery images the first time they're shown (also while skipping) and endings when reached, across every playthrough on the device, alongside achievements; the Extras screen (from the title) lists them with locked entries as ???. Scripts that need to react to progress, such as an epilogue unlocked by every ending, use `global var`.

### D-038 — The camera is scene state; shakes and flashes are not (accepted)
`camera zoom 1.5 at 70% 30% over 3` zooms the picture (backgrounds and characters, never the text) toward a point. The camera is part of the scene, so saves, going back and starting from a line all show it where the script left it, and a new `scene` resets it. The zoom keeps the chosen point fixed on screen, which means a zoom of 1 or more never shows past the picture's edges; panning is zooming toward another point. Camera moves don't block, so a slow pan plays under the next lines (`wait` to watch it). `shake` and `flash` are moments, not state, and are left out when skipping, going back or with reduced motion. A flash waits only until the screen is covered, so a `scene` right after it changes unseen. `shake`, `flash` and `camera` aren't reserved words, so existing characters with those ids keep working.

### D-039 — Layered characters are declared in the script, one option per group (accepted)
`layered mira:` lists `always` layers and `group`s of options, bottom first; showing an option replaces only its own group's layer, and `-option` takes an optional group's layer off. This is the model writers know from Ren'Py's layered images, kept to what covers most games (no conditions or auto-picked layers). Options use the same attribute syntax as plain images, so `mira smile: Hi` works whether Mira is drawn as one image or as layers, and a game can switch to layers without rewriting its script. The player stacks one `img` per layer in the sprite box rather than compositing them into one picture, so each layer loads and caches on its own and swapping a face reloads only the face.
