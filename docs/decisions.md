# Decisions log

Short records of decisions that shape the project. Newest at the bottom. Status: **accepted**, **provisional** (revisit soon), or **superseded**.

---

### D-001 — Name: Emaki (accepted)
*Emaki* (絵巻, "picture scroll", pronounced eh-MAH-kee) are Japanese illustrated handscrolls from the 12th century onward: pictures and text read scene by scene as the scroll unrolls. They are an ancestor of the visual novel, a story told through pictures and words, one scene at a time.
Short, meaningful, rarely used in software, and works as a CLI name (`emaki`), a package scope (`@emaki/*`) and a "Made with Emaki" credit. Chosen over Lantern (too generic), Benshi, Kamishibai, Limn and Quire. Formal trademark checks are deferred.

### D-002 — License: MIT, no royalty on the core (accepted)
The engine, editor and exports are free forever. Ren'Py is free and MIT, so any fee on the core would be a reason not to switch, and royalties can't be enforced on OSI-licensed code anyway. If paid offerings ever exist, they will be optional services around the engine (for example console-port support or cloud builds), never a tax on the core or on games made with it.

### D-003 — TypeScript for everything in v0 (accepted)
Biggest contributor pool, the editor is a web-UI problem, and web/mobile become native targets instead of ports (Ren'Py's weakest areas). Consoles later via a native player that implements the compiled format (D-005).

### D-004 — No build step: Node type stripping + `.ts` imports (accepted)
Node ≥22.18 runs `.ts` directly; Vite and Vitest handle the same files. Packages export `src/index.ts`. Constraint: erasable TypeScript only (no enums/parameter properties/namespaces). Revisit if we publish to npm (we'd add a build that emits `.js` + `.d.ts`).

### D-005 — Compile to a portable JSON instruction list (accepted)
Source `.vn` → AST → flat instruction array with resolved jump targets + expression trees as JSON. Any runtime (TS today, Rust/C++ for consoles later) implements ~14 opcodes and a tiny expression evaluator. Spec: docs/story-format.md. Versioned by `FORMAT_VERSION`.

### D-006 — Screenplay-style, indentation-based syntax close to Ren'Py (accepted)
Writers already know Ren'Py; it makes the planned Ren'Py importer easy. Differences from Ren'Py, on purpose:
- Dialogue text is **unquoted** (`mira: Hello.`), like a screenplay. Quotes are optional.
- `set x += 1` instead of `$ x += 1`: no embedded Python; a small sandboxed expression language (`and`/`or`/`not`).
- Variables must be declared (`var trust = 0`) so typos are caught at compile time.
- Reaching the end of a label **returns** (or ends the story) instead of falling through into the next label. Fall-through is a classic Ren'Py bug source.

### D-007 — Sandboxed expression language, not JavaScript (accepted)
Portable to native runtimes, can't touch the host, statically analysable (free variables → typo detection, reachability). Escape hatch for power users will be a plugin API, not inline code.

### D-008 — Stable line ids = label + hash(speaker|text) (provisional)
Used for localization keys, live-reload resume, and (later) save robustness. Editing a line changes its id, which is correct for translation ("this line changed, re-translate"). Duplicates in the same label get a `.2` suffix. Revisit: optional explicit ids (`#id`) for lines writers want to pin.

### D-009 — Runtime is a headless VM producing Steps (effects + one blocking event) (accepted)
DOM-free so it's testable in Node and reusable by any renderer. Rollback = snapshot per blocking event (bounded, 500). Saves = full state snapshot + story hash. Live-reload `resume()` relocates by line id when the story changed.

### D-010 — DOM/CSS renderer first, WebGL later (accepted)
v0 player is plain DOM: accessible, crisp text, tiny (≈13 KB gzipped incl. engine). The Effect/Block contract lets a PixiJS/WebGL renderer drop in later for shaders/particles without touching the VM.

### D-011 — Sprite attributes replace, they don't merge (provisional)
`show mira smile` then `mira sad: ...` → attrs become `[sad]`. Simpler than Ren'Py's attribute merging; revisit when layered sprites (outfit + expression) arrive.

### D-012 — Comments are full-line `#` only (superseded by D-057)
Inline comments would conflict with dialogue text containing `#` ("mira: Room #4"), so a comment is always a whole line. Comments are preserved by the formatter; see D-015.

### D-013 — The story map is a dev-only tool (accepted)
The flowchart of scenes, play-from-here and live variable editing exist to help writers test routes. They are loaded lazily on the dev server only: the Vite plugin emits the story graph only when serving, and the map module sits behind `import.meta.env.DEV`, so published games never ship a spoiler map of their own routes or the extra code. A player-facing route chart (as some VNs offer after completion) would be a separate, opt-in feature.

### D-014 — Flowchart layout is home-grown, not a dependency (accepted)
A small Sugiyama-style layered layout (back-edge detection, longest-path layering, barycenter ordering) in `player-web/src/map/layout.ts`. Story graphs are small (tens to a few hundred labels), so a ~200-line pure function beats pulling in dagre/elkjs. It is DOM-free and tested, so the future editor can reuse it. Revisit if large stories need better edge routing.

### D-015 — Comments and blank lines live in the AST as "leading trivia" (accepted)
Every node (declaration, label, statement, menu choice, elif/else branch) can carry `leading: string[]`: the comments ("# ...") and blank lines ("") written directly above it. Comments after the last line go in `Program.trailing`. The printer writes them back, so the formatter and the future visual editor never lose a writer's notes.
The AST is kept canonical so `parse(print(ast))` equals `ast`: consecutive blank lines collapse to one, and a blank line is dropped where the printer always puts one anyway (start of a block, before each label, before the first item of each declaration group). Canonical files round-trip byte for byte (`print(parse(text)) === text`), and CI checks the demo with `emaki fmt --check`.
A comment attaches to the next line regardless of its indentation, so a note left at the end of a block moves to the line after the block when formatted. Simple and predictable; revisit if writers find it surprising.

### D-016 — Text styling is Markdown-like and compiled into spans (accepted)
`*italic*`, `**bold**` and `[color=...]...[/color]`, because writers already know Markdown, and square-bracket tags can't clash with `{variable}` interpolation. Markup is parsed at compile time: instructions keep plain `text` and gain optional `spans`, so the format change is additive (`FORMAT_VERSION` stays 1) and a variable's value can never be mistaken for markup. Unbalanced markers are errors, not guesses. Quoted strings keep unknown backslash escapes such as `\*`, so escaping works the same quoted or unquoted.

### D-017 — Player settings are per game, validated, and applied through CSS variables (accepted)
Text speed, auto-advance wait, volumes, text size, text box opacity, font and animations. Stored in localStorage per game title; every value is clamped or defaulted on load, so a bad stored value can't break the player. Visuals are driven by CSS variables and classes on the stage, so themes can restyle without touching code. "Animations: follow my device" is the default, respecting `prefers-reduced-motion`.

### D-018 — The stage adapts to its host: 16:9 letterbox when wide, full-screen portrait when tall (accepted)
The player marks the element it mounts into as a CSS size container and lays out from the host's shape, not the window's, so the dev story map, an embed or a phone all behave the same. Hosts taller than 4:5 get the portrait layout: the stage fills the host, backgrounds crop to the centre, characters stand above a full-width textbox, and the quick menu sits below it in one row. Everything inside sizes off one unit, `--u` (1% of stage height in landscape; tied to the width in portrait), and sprite positions are CSS variables (`--pos-left/center/right`), so a theme can retune either layout without code. Games are still authored for 16:9; per-image focal points for portrait cropping can come later. **Amended 2026-11-20:** a game with a `canvas:` header places its pictures and screens in pixels on that canvas, which the portrait layout stretched (a narrow editor pane showed a ported title screen squashed); such games are always letterboxed at their own aspect, on phones too (the host's container gets another name, so the portrait rules don't match). The rule became the header `orientation:` the same day (D-069).

### D-019 — Preloading is a static lookahead in the runtime; the player waits briefly, never forever (accepted)
`Runner.upcomingImages()` walks the compiled code from the current position without running it: every branch of conditions and menus, into calls and back out, up to a few lines/menus away (and a hard cap on instructions visited). That keeps it deterministic and testable without a browser, and any future runtime gets the same behaviour. The web player keeps the results loaded and decoded (a small most-recently-used cache) and, when a step changes the picture, holds that step for at most 1.5 s until its images are ready, so nothing fades in half-loaded. A slow or missing file never blocks the story, and skip mode doesn't wait at all.

### D-020 — Editor support lives in an editor-agnostic module; the VS Code extension is a thin, bundled adapter (accepted)
`packages/language` (originally `packages/vscode/src/language.ts`) implements problems, symbols, definition, references, hover, completion and formatting as plain functions over text and 0-based positions, built on the real compiler, so the editor always agrees with `emaki check`. It has no VS Code imports, is unit-tested, and can back a language server or the web editor later. `extension.ts` only translates to the VS Code API. This is the one package with a build step: VS Code can't run TypeScript, so esbuild bundles the extension and the compiler into a single file that needs nothing installed. The TextMate grammar is tested with `vscode-textmate`, the engine VS Code itself uses. Not yet on the Marketplace.

### D-021 — Line previews rebuild the scene by replaying the label, not by running the story (accepted)
`Runner.startAtLine(n)` starts at the first instruction on or after line `n`. To avoid opening on a black screen, it replays the `scene`/`show`/`hide`/music statements from the top of that label down to the line, ignoring conditions and menus (when two branches both change the picture, the later one wins). Running the story from the start instead would need a path of choices to reach the line, which may not exist for the variables being tested. The approximation is predictable, covers the usual case (a label sets its scene near its top), and the writer can set variables in the link (`?line=52&trust=2`). Previews are dev-only: a published build ignores `?line=`. After a live reload the player resumes where it was, unless the address changed, so following a new preview link always wins.

### D-022 — Accessibility fonts are bundled with every game, loaded on demand (accepted)
Players can switch story text to Atkinson Hyperlegible (designed for low-vision readers) or OpenDyslexic. Both are SIL Open Font License, so any game, free or commercial, can ship them; they come from `@fontsource` packages and are bundled into the build rather than fetched from a font CDN, so games work offline and don't contact third parties. Only `@font-face` rules are loaded up front: a font's files download the first time a player picks it, so a game that nobody switches costs nothing extra. OpenDyslexic's large letters are evened out with `font-size-adjust`.

### D-023 — Demo audio is downloaded CC0, not generated; the player keeps plain HTML audio for now (accepted)
Games bring their own audio; the demo only needs enough to exercise the audio path and sound decent. We use CC0 recordings from OpenGameArt (credited anyway in `CREDITS.md`, shipped with the build) rather than synthesising placeholder tracks, which would be code nobody needs. CC-BY assets were passed over so the demo carries no attribution obligations. Files are MP3 because every browser plays it. Playback stays on `HTMLAudioElement`: `fade` now works for `play` and `stop` (a new track crossfades over the old one), and sound effects are not played when skipping, rolling back or loading, so they don't fire in bursts. Known limit: MP3 loops can have a tiny gap at the loop point; gapless looping through Web Audio is on the roadmap, along with an ambience channel that can play under music.

### D-024 — Reduced motion doesn't change text speed (accepted, amends D-017)
Previously "reduced motion" also made text appear instantly. That surprised players: Windows reports reduced motion whenever "Animation effects" is off, a common setting, so their text never typed out, even though Text speed was set. Reduced motion is about movement (fades, slides, bouncing indicators), and letters appearing in place isn't movement. Typing is now controlled only by Text speed, which has its own Instant option. Reduced motion still makes transitions instant and stops the next-line indicator from bouncing.

### D-025 — The editor is a local web app over the game folder, built from the engine's own parts (accepted)
`npm run edit` serves the editor with Vite, the same way `npm run dev` serves the game. A small plugin gives the page one API, read and save `story.vn`. The text on disk stays the single source of truth, so writers can use the editor, VS Code and git on the same file at once. The editor reuses everything it can. The script pane is CodeMirror 6 driven by `@emaki/language` (moved out of the VS Code extension for this), so both editors report the same problems. The game pane is the real web player. The flowchart uses the story map's layout. As you type, the script is recompiled and `Player.reload()` swaps in the new story at the same line through `Runner.resume()`, the same path live reload uses, so music and the scene carry on.
Saving is automatic, a moment after typing stops. Every save says which version of the file it was based on (a hash). If the file changed on disk in the meantime, the save is refused and the writer chooses which version to keep. A change on disk is loaded silently only when the editor has no unsaved edits. Writes go to a temporary file that is then renamed, and keep the file's line endings. The API only answers requests from the editor's own page, so another website open in the browser can't rewrite the script. A desktop wrapper (needed anyway for exports, Milestone 3) can reuse all of this. Revisit: editing several `.vn` files once stories can span files.

### D-026 — Visual edits are tree edits printed back to text; the script stays the source of truth (accepted)
The flowchart and the asset browser never keep their own copy of the story. Each action (add, rename, delete or connect a scene, declare or drop an asset) is a pure function in `@emaki/language/edits`: it parses the script, changes the syntax tree and prints it with the printer. That gives canonical text with every comment kept (D-015). The editor applies the result as an ordinary edit, so it is saved, played and undone (Ctrl+Z) exactly like typing. A script with syntax errors is never edited, because printing an incomplete tree could drop lines; the writer is told to fix the error first. Because the printer is canonical, the first visual edit to an unformatted script also tidies its layout (the same as `emaki fmt`).
The edits are deliberately conservative. Deleting a scene is refused while anything still leads to it, and so is deleting the start scene. Connecting a scene appends a `jump` if it just ends. If it already jumps, the jump becomes a `menu` with a placeholder choice for each destination ("(Choice) Kitchen talk"), and a scene that ends in a menu gets one more choice. A scene that `return`s is left alone. The rules for anything subtler are better expressed in text, and the flowchart shows exactly where (click an arrow to see its line).

### D-027 — Assets dropped into the editor are copied in, never overwritten, and named from the file (accepted)
Files dropped from the computer go to `assets/images/` or `assets/audio/` under a cleaned-up name. If a file with that name exists, the same bytes reuse it and different bytes get a numbered copy, so nothing a writer made is ever replaced. Declarations are named from the file name: `Cliff Road (dusk).png` becomes `cliff_road_dusk`, a `bg_` prefix is dropped, and a file starting with a character's id (`mira_smile.png`) becomes that character's sprite, `mira smile`. Dropping an asset inside a scene also adds the statement: `scene` for a single name, `show` for a sprite, `play music` (or `play sound` for files in an `sfx`/`sound` folder). Uploads are accepted only from the editor's own page and only for image and audio types.

### D-028 — Translations are catalogs keyed by line id, in PO or CSV; the runtime swaps text by id (accepted)
A translation is a file per language in the game's `lang/` folder: `fr.po` for translation tools (Poedit, Weblate and Crowdin all read gettext PO), or `fr.csv` for spreadsheets. Each entry is keyed by the line's stable id (D-008), which goes in `msgctxt`, so identical sentences in different scenes can be translated differently. The compiler lists every string a player reads (lines, choices, character names, the title, achievements) with its id and raw source text, markup included, so the exporter and the runtime can't disagree about ids. The player's own buttons (`ui.*`) go into the same file, so a translated game is translated all the way through, not just its story.
`emaki strings --lang fr` creates or updates a catalog. Existing translations are kept. Because a line's id hashes its text, editing a line gives it a new id; the update then offers the closest old translation from the same scene (word-level similarity of 0.5 or more) as a *review* entry (fuzzy in PO). Translations for deleted lines are kept as obsolete, so no translator's work disappears. The game uses only reviewed (`ok`) entries and shows the original for anything else. Compiling a translation checks its markup, and refuses `{variables}` that the original line doesn't use, because a typo there would show players "{nmae}".
At runtime `Runner.setTranslation()` swaps text by id when blocks are built. Switching language mid-scene redraws the current line, and rollback, loads and the history log follow the new language. The player picks a language from Settings, which defaults to matching the device's languages (an exact match first, then the base language, so `pt-BR` falls back to `pt`), and sets `lang` and `dir` (right-to-left) on the stage. Plural forms are not supported yet; PO entries that use them are reported and ignored.

### D-029 — Desktop export uses Electron, not Tauri (accepted)
Tauri makes much smaller apps (a few MB instead of about 300 MB unpacked), but it renders with each system's own web view: WebView2 on Windows, WebKit on macOS and WebKitGTK on Linux, which differ in audio, fonts and CSS container queries (the player relies on these, D-018). It also needs a Rust toolchain on every developer's machine. Electron ships one known Chromium everywhere, so a game looks and sounds the same as in the dev server, and it exports with nothing but npm: `@electron/packager` downloads the right Electron for each target, so one machine can build for Windows, macOS and Linux. The shell (`packages/desktop/app`) is small, plain JavaScript shipped as-is. It serves the game over a private `app://` scheme, because `file://` can't load module scripts. Pages get no Node access (context isolation, sandbox), and the only bridge is the `EmakiHost` interface. Chromium's interface translations, which a game never shows, are trimmed to English plus the game's languages (about 45 MB saved). Revisit Tauri if download size becomes the main complaint, once system web views have caught up.

### D-030 — Steam support is optional, through steamworks.js, behind the host bridge (accepted)
A game gets Steam by adding `steam_app_id` to its header. Only then does the desktop export include `steamworks.js` (MIT, prebuilt for each platform, with Steam's own library), unpacked outside the asar archive so it can load. The shell starts Steam before the window opens (needed for the overlay), and maps `achieve <id>` to the Steam achievement with the same id. If Steam is unavailable, the game runs without it. Achievements themselves are part of the language (`achievement id "Name"` declares one, `achieve id` awards it), so the compiler catches typos, names are translatable, and every platform behaves sensibly: Steam's popup on Steam, an in-game notice and local record everywhere else. The player reaches platform features only through `window.emakiHost` (quit, full screen, achievements, back button), which each shell provides as far as it can, so the same web build runs everywhere. The compiled format gains an optional `achievements` table and an `achieve` op; like styled spans (D-016) this is an addition, so `FORMAT_VERSION` stays 1 until the format is first published.

### D-031 — Phone export generates a Capacitor project once and only syncs it afterwards (accepted)
`emaki export android|ios` writes a Capacitor project to `<game>/export/mobile`. The first export runs `npm install` and `cap add`; later exports copy the new web build in with `cap sync`. Native changes made in Android Studio or Xcode (signing, icons, store settings, orientation) therefore survive re-exports, and the generated projects are ordinary ones that any Capacitor guide applies to. The engine itself depends on no Capacitor package: the project pins compatible versions, and the player finds the App and StatusBar plugins on `window.Capacitor` at run time (for the back button, quitting on Android, and a hidden status bar). An APK is built only when the Android SDK is found. Otherwise, and always for iOS off a Mac, the export prepares the project and says exactly what to do next. Signing for the stores stays in the native tools, where store requirements change.

### D-032 — Skip stops at unread text by default (accepted)
The player records which lines have been read, by line id (D-008), across every playthrough on the device, and skip stops at the first line not read before. That is what makes replaying a branching story for its other routes bearable, and what players of the genre expect. Because a line's id hashes its text, a line the writer changes counts as unread again, which is right: it is new text. Settings has "Skip: Text you have read / All text" for players (and writers testing) who want the old behaviour. The record is one JSON list per game, written in batches so skipping thousands of lines doesn't write to storage on every line.

### D-033 — The title screen is customized in three layers (accepted)
Header keys cover what most games need (`title_image`, `title_music`, `title_logo`, `title_layout`, `title_buttons`). A `theme.css` in the game folder restyles anything, against a documented, stable set of class names (docs/theming.md). For full control, a label named `title` *is* the title screen: it plays like any scene, and its `menu:` becomes the title menu, followed by the built-in Load, Settings and Quit. This keeps title screens in the story language rather than a separate screen language: conditions, `global var` unlocks, translations and the editor all work on them unchanged. A choice on the title starts a new game from that choice, with rollback cleared so going back can't return into the title. `title` is never chosen as the start label by default and always counts as reachable.

### D-034 — A story can span many files; story.vn is the main one (accepted)
Every `.vn` file in the game folder (except in assets, lang, dist, export and tools) is part of the story, with one shared namespace: no `include` lines to keep in order, and scenes can move between files freely, because line ids depend on the label and text, not the file. Only story.vn has a header. The compiler parses each file, tags every location with its file, and compiles the merged program, so diagnostics, source references in the compiled story, the story map, preview links (`&file=`) and translation references all name the file. Locations in story.vn carry no file, which keeps single-file stories and their compiled output exactly as before. The editor and VS Code analyse each file with the others' current (unsaved) text, and the flowchart's scene edits work across files (renaming updates jumps everywhere).

### D-035 — Engine features come from real games (process)
Porting a complete existing visual novel (34 scripts, about 4,600 lines, 1,700 voice files, three endings) was used to find what Emaki couldn't yet express. The conversion script stayed outside the repository; only general features the port proved necessary were added: `aspect`, real sound and voice channels, percentage positions, `global var`, `narration: plain`, read-text skip, the scripted title screen and multi-file stories. New features should keep coming from games like this rather than from feature lists.

### D-036 — NVL mode is part of the story state, and pages turn over by themselves (accepted)
`nvl on` switches to pages of full-screen text, `nvl off` back to the text box, and `nvl clear` starts a new page; `nvl: on` in the header starts a story that way. The lines on the current page are kept in the runner's state (at most 40; a page shows fewer), so rollback, loading and switching language redraw exactly what was on screen. The player lays a page out from its first line and starts a fresh page when the next line wouldn't fit, the way a printed or DS novel does, so writers rarely need `nvl clear`; a new `scene` also starts a new page. The typewriter writes into whichever element shows the current line, so typing, auto, skip and voices behave the same in both modes.

### D-037 — Extras come from declarations, and progress is per device (accepted)
A gallery image is an ordinary image declared with `gallery`; an ending is declared with `ending id "Name"` and reached with `end id`. Keeping both in the script means the compiler checks them (an `end` with a misspelled ending is an error), their names are translatable, and the Extras screen needs no separate configuration. The player records gallery images the first time they're shown (also while skipping) and endings when reached, across every playthrough on the device, alongside achievements; the Extras screen (from the title) lists them with locked entries as ???. Scripts that need to react to progress, such as an epilogue unlocked by every ending, use `global var`.

### D-038 — The camera is scene state; shakes and flashes are not (accepted)
`camera zoom 1.5 at 70% 30% over 3` zooms the picture (backgrounds and characters, never the text) toward a point. The camera is part of the scene, so saves, going back and starting from a line all show it where the script left it, and a new `scene` resets it. The zoom keeps the chosen point fixed on screen, which means a zoom of 1 or more never shows past the picture's edges; panning is zooming toward another point. Camera moves don't block, so a slow pan plays under the next lines (`wait` to watch it). `shake` and `flash` are moments, not state, and are left out when skipping, going back or with reduced motion. A flash waits only until the screen is covered, so a `scene` right after it changes unseen. `shake`, `flash` and `camera` aren't reserved words, so existing characters with those ids keep working.

### D-039 — Layered characters are declared in the script, one option per group (accepted)
`layered mira:` lists `always` layers and `group`s of options, bottom first; showing an option replaces only its own group's layer, and `-option` takes an optional group's layer off. This is the model writers know from Ren'Py's layered images, kept to what covers most games (no conditions or auto-picked layers). Options use the same attribute syntax as plain images, so `mira smile: Hi` works whether Mira is drawn as one image or as layers, and a game can switch to layers without rewriting its script. The player stacks one `img` per layer in the sprite box rather than compositing them into one picture, so each layer loads and caches on its own and swapping a face reloads only the face.

### D-040 — Voices are found by line id, from files that exist (accepted)
A header `voice: voice/{speaker}/{id}.ogg` says where every line's voice would be. When the whole game is compiled (CLI, dev server, export), Emaki looks for each line's file and stores the ones that exist in the compiled story, outside the story's hash, so recordings can arrive one session at a time without missing-file requests for the rest or invalidating saves. Ids are the same ones translations use, which is how Ren'Py's auto-voice works too; the cost is that editing a line orphans its recording, so `emaki voices` writes the recording script and lists files no line uses. An explicit `play voice` before a line still wins. The voice a line played is kept on the line, so the history log can replay it.

### D-041 — Loops play through Web Audio; ambience is its own channel (accepted)
An `<audio loop>` element pauses for a moment each time it wraps around, which ruins music written to loop seamlessly and makes rain stutter. Looping tracks (music, ambience, looping sounds) are decoded and looped by Web Audio, which is sample-exact; tracks that play once, and files Web Audio can't decode, still use `<audio>`. Decoded audio is large (about 10 MB a minute), so only the last four loops stay decoded. `ambience` is a fourth channel because a scene's background (rain, wind, a crowd) outlives its sound effects: `stop sound` cuts the effects without silencing the weather, and the ambience, like the music, is part of the story's state, so loading and going back bring it back.

### D-042 — Side images by naming convention; per-character boxes through CSS (accepted)
A side image is an ordinary image whose tag is `side`: `image side mira smile`. The runner remembers each character's latest attributes (from dialogue and `show`, only in stories that have side images) and picks the most specific `side` image they all match, so `mira smile:` followed by `mira:` keeps the smile even when Mira has no sprite on screen. Attributes that only a side image uses don't touch the sprite. This follows Ren'Py's convention, which writers moving over already know. Per-character text boxes need no new syntax: the box carries `data-speaker`, so `theme.css` can give a radio voice a monospace font or a narrator a different background with one rule.

### D-043 — Pictures with text in them are translated by file name (accepted)
A CG with a sign, a letter or sound-effect lettering needs a version per language. The translated picture sits next to the original with the language code before the extension (`cg/sign.png` → `cg/sign.fr.png`, `cg/sign.zh-Hant.png`), and the game uses it whenever that language is chosen; pictures without a version stay as they are. This needs no new syntax and no catalog entries (a translator who can draw adds files, nothing else), and it works the same for backgrounds, sprites and their layers, side images and the gallery. As with voices (D-040), the compiler looks for the files when the whole game is built and stores the ones that exist in the compiled translation, so the player never asks for pictures that aren't there. Switching language redraws the scene. Device languages are matched by script as well as base language, so `zh-TW` and `zh-HK` players get `zh-Hant` and `zh-CN` players `zh-Hans` (found while porting a VN released in Japanese, English and both Chinese scripts).

### D-044 — Character moves are named, not keyframed (accepted)
`hop mira`, `nod mira 2`, `bow mira` and `shake mira` (and the same on `textbox`) cover what VNs use small sprite moves for: surprise, agreement, greeting, refusal. Porting a commercial VN showed these four account for nearly all of its 1,800 character and text box actions. Named moves read like stage directions, need no animation vocabulary, and keep the format portable: a runtime only has to know four moves. Distances are fractions of the screen's height, so they look the same at any size. Like `shake` and `flash`, moves are moments, not state: they don't block the story, and skipping, rollback and reduced motion leave them out. A general transform language (Ren'Py's ATL) stays out of the core; endless loops (a floating icon) are left for later, since they would have to become scene state.

### D-045 — Movies block the story and are skippable (accepted)
`movie "path"` plays a video over the stage and the story waits for it, the way openings and endings work in commercial VNs. A click, Enter, Space or Escape skips it, without also advancing the line underneath; skipping mode and rollback never play it. It plays at the music volume, and falls back to muted when the browser blocks sound. Movies are an effect rather than state, so loading a save never restarts one. Versions per language use the same file naming as pictures (D-043): the compiled translation's `images` map became `assets` and covers movies too, before any game depended on the old name.

### D-046 — Endless moves are sprite state (accepted)
`float mira` and `shake mira forever` repeat until `still mira`. Unlike one-off moves (D-044), an endless move is something the player should still see after loading a save or going back, so it is stored on the sprite (`loop`) and the player restarts it whenever it redraws the scene. Tying it to the sprite means `hide` and a new `scene` end it with no extra bookkeeping. The text box can't loop: a permanently shaking box would be hard to read. Reduced motion leaves loops out.

### D-047 — Colour tones are scene state that outlives the scene (accepted)
`tone sepia` / `tone mono` / `tone none` tint backgrounds and characters but not the text, which stays readable. A flashback usually spans several backgrounds, so a tone survives `scene` (unlike the camera) and lasts until changed. Two named tones cover what VNs commonly use this for (the past, memories); arbitrary colour matrices stay out of the core until a game needs one. The player animates the tone with Web Animations, separately from the camera's transform transition on the same layers.

### D-048 — Furigana is markup: `[ruby=reading]text[/ruby]` (accepted)
Japanese VNs annotate unusual readings, and translations into Chinese sometimes keep them. Ruby follows the colour tag's form, so writers learn one bracket syntax, and it compiles to a `ruby` field on a span, which never merges with its neighbours. Plain `text`, the history log and screen readers get the base text alone; the player renders a real `<ruby>` element and centres the base under a longer reading rather than spreading its characters apart.

### D-049 — Screens are a small declarative language in the script (accepted)
A game's own title screen and menus are written as `screen name:` blocks in the script, not in HTML or a general-purpose language. Elements are one line each (`button "New Game" image "ui/new.png" -> start if visits > 0`) and compile to a JSON tree, so the compiler checks labels, variables, images and screen names, translators get the text through the usual catalogs, and any future runtime can draw them. Screens can't run code: they have a fixed set of actions (start, continue, open, close, title, quit, jump, set) and conditions, which covers unlockable extras and route menus while keeping saves and the sandbox safe. Layout is placement plus rows, columns and boxes; appearance belongs to `theme.css`. Positions take percentages or pixels on a declared `canvas`, converted to percentages at compile time, so UI art drawn at a fixed size lines up exactly and still scales. Every button needs a text label even when it's a picture, because that is its accessible name and what gets translated. `screen title` and `screen menu` replace built-in screens; replacing load/save/settings needs slot and setting elements and comes next. Proved on a commercial VN's demo, whose title screen was generated from the original layout tables and matches the original.

### D-050 — Data screens bind to the player, not to code (accepted)
Save/load, settings and extras screens need data the script can't compute: what's in each save slot, the player's settings, what's been unlocked. Rather than open the screen language up to code, it gets elements that are bound to that data: `slots N -> load|save` (cells laid out by the writer, with `{slot_date}` and friends, and paging), `thumbnail`, `gallery`, `endings`, `achievements`, and `slider`/`toggle`/`choice` bound to named settings. Thumbnails are the saved scene redrawn from the save itself (background, characters, tone, styled by the game's theme) instead of screenshots, so saves stay small, old saves get pictures too, and nothing depends on a browser being able to capture its own page. `save_slots` in the header sets how many slots a game has (3 by default, for games that never replace the screen). A game's `screen save|load|settings|extras` replaces the built-in one wherever it opens, and every control keeps a text label for screen readers and translators.

### D-051 — Screens during the story are state, and a called screen is a blocking event (accepted)
`show screen hud` and `hide screen hud` change a list of shown screens that is part of the story's state, like the scene, so saving, loading, going back and line previews all bring the right screens back without the player having to redraw anything. `call screen map -> place` is a blocking event like a menu: the runner stops on it and goes on only through `returnFromScreen(value)`, which a button's `-> return value` action calls; going back returns to the waiting screen with the variable as it was. A called screen is the open-ended version of `menu`: the writer lays the choices out (pins on a map, apps on a phone) and decides what each returns. Screens over the story are drawn in their own layer between the text box and the quick menu, so a full-screen one still leaves save, load and settings in reach, and the player's own screens (title, menu, save, load, settings, extras) can't be shown this way because they belong to the player, not the story.

### D-052 — The text box is a screen that places the player's own parts (accepted)
`screen textbox` doesn't rebuild the text box: it places the player's existing line, name and side image elements (`dialogue`, `speaker`, `side`) among the game's own art and buttons. Typing, pauses, styled text, voices, read-text skipping and the screen-reader live region keep working unchanged, because they are the same elements. The screen sees a `speaker` variable so name plates can depend on who talks, buttons on it take the place of the quick menu, and new actions (`back`, `auto`, `skip`, `hide`, `quicksave`, `quickload`, `voice`) give a text box of its own every control the built-in quick menu has. The text box is redrawn every line, so its buttons always reflect what can be done.

### D-053 — Picture states, settings as buttons, and input that needs no setup (accepted)
Commercial UI art comes as sprite sheets of states, so buttons and slots take a picture for each state: idle, `hover`, `pressed`, `selected` and `disabled`. "Selected" is computed, not declared: a button is selected while its action is in effect (auto on, its page or tab showing, `setting name value` holding), which covers radio-style option pictures, tabs and page numbers without variables. Picture sliders are a gauge revealed up to the value plus an optional knob, the common VN shape. Gamepads work on every screen without a focus order: the d-pad picks the nearest control in that direction. Fades (`screen x with fade`), click and hover sounds (header keys) and the editor's live screen preview round it off. Proved on a commercial VN's demo: its title, text box, save, load and four settings pages were generated from the original layout tables and look like the original, with settings Emaki doesn't have drawn as their defaults.

### D-054 — The history, questions and audio mix are the game's to draw (accepted)
The last built-in pieces a commercial UI replaces become screens: `screen history` with a `log` window element (entries laid out by the writer, with per-entry `voice` and `rewind`, scrolling by line or window), and `screen confirm` for every question the player asks before something can't be undone. Questions are one generic flow (`ask(kind)`), so each can be switched off by a `confirm_<kind>` setting and drawn by kind (`{confirm}` picks the picture with the question drawn in). The audio mix gains a master volume, mutes that keep their level, and per-character voice volume and mute keyed by `define` id, because the voice that plays always knows whose line it is. Skipping to the next choice (through unread text) and back to the previous one, `reset` and voice `sample` buttons complete the controls a VN settings screen carries. Proved on the same demo: backlog, yes/no dialog, the sound page (master, channels, ten characters, test buttons) and the dialogs page all work as in the original.

### D-055 — Plugins: code beside the story, described to the compiler (accepted)
The escape hatch D-005 promised. A plugin is a folder in the game (`plugins/<name>/`) with a `plugin.json` manifest and an `index.js`. Scripts call it with `@name command key=value` lines (and `@name element` in screens): the `@` keeps plugin names from ever clashing with characters or future statements, and named arguments keep calls readable and checkable. Because the manifest declares every command, element and argument type, the compiler, CLI, editor and exports check plugin use without running plugin code, the same way they check labels and variables; only a tool that doesn't know the game's plugins (VS Code, for now) skips those checks. Commands are effects, or block the story (`waits`, with a result into a variable, like `call screen`). Lasting effects are part of the saved state as the command and its arguments, and come back by being run again after the plugin's `reset()`, so plugins never handle saves, rollback or line previews themselves. Plugins can only read variables; the story changes only through results. Events (line, choice, ending, achievement, save, load) cover analytics and integrations. A plugin is trusted like the rest of the game (no sandbox); a failing plugin is logged and never stops the story. Functions in expressions (`roll(6)`) are left for later, until their interaction with rollback is designed (done in D-058).

### D-056 — Scene replay and the music room unlock like the gallery (accepted)
Both are declared in the script and unlocked by playing, like `image ... gallery`: `audio ... music "Title"` marks a track for the music room, unlocked once it plays as music, and `replay label "Name"` marks a scene, unlocked once one of its lines is shown, both remembered across playthroughs on the device. A replay is a mode of the runner, not a copy of the scene: it starts at the label with fresh variables (globals kept) and the story ends where it leaves the label at the top of the call stack, so calls stay part of the scene; `until label` covers scenes written across several labels. Replays can't be saved, and they end back on the Extras screen they started from. The music room swaps the music for its track and puts back what was playing when the player leaves it. The built-in Extras screen gets Scenes and Music tabs; a game's own screen uses the `scenes` and `music` elements. On the ported demo, the music room lists the 37 tracks it ships, in the original's order, behind its title's Music button.

### D-057 — End-of-line comments: a `#` with spaces around it (accepted)
Writers asked for notes beside a line (`scene kitchen  # morning light`), which D-012 ruled out because dialogue can hold `#` ("Room #4"). The rule that keeps both: a `#` starts a comment only with a space before it and a space (or the line's end) after it, outside double quotes. Hashtags, room numbers and colours (`#4`, `#e8b04b`) stay text; the rare dialogue with a free-standing ` # ` is quoted or written `\#`, and the formatter quotes such dialogue itself so its output always reads back the same. No existing script in the demos or ports changed meaning. Comments live in the AST as `comment` beside `leading` (D-015), header entries included, so the formatter and the visual editor keep them, written two spaces after the line.

### D-058 — Plugin functions in expressions: `@plugin.function(args)` (accepted)
Plugins can now answer questions as well as run commands: `if @dice.roll(6) > 4:`. The `@` keeps them apart from variables (and from any built-in functions later), the `.` from commands, and the arguments are positional, like functions everywhere, with optional ones last; the manifest's `functions` table lets the compiler check the plugin, the function, the number of arguments and literal values, as for commands. Calls are part of the expression tree, so every place that evaluates an expression can ask: the runner through `Runner.callPlugin`, screens through their host. Functions are synchronous and answer with a number, text or boolean; anything else, or an exception, stops the story with a message naming the function, because a condition can't go on without its value. On rollback: the story doesn't record answers. Going back restores the variables as they were, and playing on evaluates the expression again, so a random function may answer differently, which keeps plugins free of save and rollback concerns, the same trade D-055 made for lasting commands. Starting values can't call plugins, since they're computed at compile time. Editors get the manifests too (VS Code reads plugins/*/plugin.json beside the story and watches it), so `@` lines are checked and completed everywhere.

### D-059 — Story files are packed; runtimes expand them on load (accepted)
A full-length game (80,000 lines, three routes) compiled to 31 MB, and 44% of it was each instruction's `src`, which repeats the same file and label on every line of a scene. Story files are now written packed (version 2): `src.file` and `src.label` only where they change, and `say` without its `who: null` and empty `attrs`. Loading expands them back, so the runtime, saves, translations and every tool keep working with the version 1 shape and nothing else changes. Runtimes in other languages implement one small loop. Packing is a file format, not a compression scheme: the result is still plain JSON that gzips well (3.6 MB for the full game), and hosts compress it in transit. The bigger change for very long games, loading the story in parts instead of all at once, is a separate decision.

### D-060 — Game data is fetched as JSON; the dev server reads assets on demand (accepted)
The story used to be written into the player's JavaScript as a module. For a full-length game that module was tens of megabytes that Vite transformed and the browser parsed as code on every reload, and builds also carried every script's source lines for an error screen only the dev server shows. Now a build writes `game.json` next to `index.html` (the packed story of D-059, the translations), and the player fetches it at startup; the dev server answers the same request from a compile it keeps until a file changes. JSON parses faster than code, the module is a few lines, and the story becomes something the player loads rather than part of its code, which is what loading it in parts would need. Every way a game is played already serves files over a URL (web hosts, the desktop app's `app://` scheme, Capacitor's local server), so the fetch works everywhere. The dev server also stopped using Vite's public folder for `assets/`, which lists and watches every file at startup (most of a minute for 31,000 pictures and voices): it reads each asset from disk when asked, with byte ranges for audio and video. Recompiles reuse unchanged files and labels (`CompileCache`), so an edit in one scene of an 80,000-line game recompiles in about a tenth of a second.

### D-061 — Loading the story in parts (proposed, not built)
After D-059 and D-060, a full-length game (80,000 lines, 187,000 instructions) is a 19 MB `game.json` (3.6 MB gzipped) that parses in about half a second and takes about 50 MB of memory. That works on desktops and current phones, so this is recorded for when a game or a device needs more, not scheduled. The shape it would take:
- **Chunks by file.** `emaki build` writes the story's shared part (header, declarations, label table) plus one chunk per script file. Targets and the label table become (chunk, index) pairs, so a chunk is relocatable and loads alone.
- **The runner asks for code.** `Runner` gets instructions through a loader instead of an array. Running into a chunk that isn't loaded is a pause the host resolves (fetch, then continue), like a plugin command that waits. Preloading follows `call`/`jump` targets and the choices on screen, so in practice the pause never shows.
- **What has to change with it:** saves store positions as (chunk, index); skipping to the next choice and back, rewinding through the history, and line previews have to cross chunk boundaries; translations and voices are split the same way. The story hash becomes a hash of chunk hashes (as it already is of label hashes, D-060).
- **What it costs:** every runtime implements the loader, which makes the format contract (D-059) bigger, and every feature that scans the whole story (reachability, skip to next choice, the story map) has to work with parts. It's worth doing when a real game needs it, for example a long game on low-memory phones, and should be measured on that device first.


### D-062 — Free layers: the picture as stacked, transformed images (accepted, 2026-11-16)
Characters on a bottom line and one background cover most visual novels, but not games whose every shot is composed: a background built from several pieces, a close-up made by zooming one picture, a character's face crossfading on a copy of her layer, light layers in `add` or `multiply`, manga-style panels with feathered edges, slow pans that keep moving under the text. A port of a full-length commercial VN uses all of these on almost every page (about 55,000 picture placements, 24,000 keyframed moves, 25 blend modes and 80 colour grades). Emaki now draws that picture itself, in the same player, instead of approximating it.

**The model.** Everything on the picture is a *layer*: a declared image with a name, a position, an anchor, a zoom (one or two axes), a rotation, an opacity, a depth, a blend mode, a colour grade and a blur. Backgrounds and characters stay what they are (`scene`, `show mira smile at left`) and are layers with defaults, so the old scripts draw exactly as before; a game that composes its shots uses the new properties.
```
show street as far at 50% 50% zoom 0.65 rotate -17.3 opacity 0.87 depth 26
show glow as light at 960 540 blend add opacity 0.5
animate far zoom 0.7 over 3 ease in-out-sine
animate light with flicker
with dissolve 0.4
```
- **Placement.** `at x y` puts the image's anchor at that point: percentages of the screen, or pixels when the game declares `canvas: 1920x1080` (screens already use it). The anchor is the middle unless the image declares one (`image aki pose = "..." anchor 56% 47%`). At zoom 1 an image's pixels are canvas pixels; without a canvas, 1920x1080 is assumed.
- **Names.** `as far` names the layer, so the same image can be on screen twice and a layer can change its picture and keep its place (`show street_night as far`). Without `as`, the name is the image's tag, as for characters today.
- **Moving.** `animate <layer> <properties> over <s> [ease <name>]` moves toward new values without holding up the story. The eases are linear and Penner's set (`in-`, `out-`, `in-out-` and `out-in-` of quad, cubic, quart, quint, sine, circ, expo, elastic, back and bounce). The state keeps the target, so a save, a load or a rollback shows the layer where it was going, as skipping does.
- **Keyframed moves.** `animation flicker loop:` declares keys (`0.4 opacity 0.6 ease out-sine`). Each key sets only what it names; the rest hold. Curves the eases don't cover are written as closer keys. `animate light with flicker` starts it, `animate light stop` ends it. Shakes, quakes and sways are animations too, so they need nothing of their own.
- **Changes shown together.** A `with` on its own line shows every picture change since the last line through one transition: `with dissolve 0.5`, or a wipe through a grey-scale rule picture, `with wipe "rules/diagonal.png" 0.8`. `scene` and `show ... with` keep working as before.
- **Colour.** `grade dusk: gamma 0.94 0.78 0.57 levels #000010 #546b90 tint #ff6500 14% overlay` declares a colour grade, and `grade dusk` on a layer applies it; `silhouette #ffffe5`, `bright 1.2`, `contrast 0.8` and `blur 6` are layer properties. Everything after the grey is a curve on each channel on its own, so one `feComponentTransfer` table per channel draws it exactly; the curve is `gradeChannel()` in the format package, the same for every runtime. `tone` (D-047) stays, and is a grade on the whole picture.
- **Panels.** `clip 0 135 1920 810 feather 32` on a layer shows only that rectangle of the screen, its edges fading over 32 pixels: letterboxes, manga-style panels. Layers that share a panel each carry its clip.
- **The text box.** `textbox hide [over s]` takes the text off the picture until the next line, for shots meant to be seen whole.
- **Sound.** `play ambience "wind.ogg" as wind` gives several loops at once; `stop ambience wind` stops one.

**How it is drawn.** The DOM player keeps one stacking order for all layers (absolutely placed elements with CSS transforms), CSS blend modes, SVG filters for grades (`feComponentTransfer` for gamma and levels, `feFlood` + `feBlend` for tints) and masks for panels; a `with` puts a frozen copy of the old picture over the new one and fades or wipes it away (a wipe steps through threshold masks made from the rule picture once). Subtractive blends have no CSS equivalent: the layer is added (`plus-lighter`) between two inversions of what is behind it (`backdrop-filter: invert(1)`), 1 - ((1 - b) + s) = b - s, which is exact. WebGL was considered: it would be exact everywhere, but it means a second renderer for pictures that the DOM already draws, and losing CSS for theming; it stays the fallback if side-by-side tests show the DOM can't match.

**Format.** New instructions `animate`, `with` and `textbox`; `show` gains a `layer` name and optional `props` (panels are the `clip` and `feather` props, not a table of their own), and the story carries `animations` and `grades`. `FORMAT_VERSION` goes to 3 (2 was already the packed files of D-059), since a runtime that doesn't know these can't draw the story.

**Proving it.** The port's converter turns the original's commands into these statements, and a harness screenshots the same moment in the original and in Emaki and measures the difference, scene by scene.
## D-063 — What Esc and a right-click do (accepted, 2026-11-16)
Commercial visual novels often show no quick menu: the player right-clicks or presses Esc to open the menu, or to hide the text and look at the picture. Emaki had no right-click at all, and Esc did nothing during the story.

**Decision.** Both open the game's menu (`screen menu`, or the settings) by default, and right-click again closes what's open. Two header keys change that: `escape:` and `right_click:`, each one of `menu`, `save` (the first empty slot), `quicksave`, `hide`, `settings`, `history`, `none`. With the interface hidden, any click, Esc or right-click brings it back first. An unknown action is a warning and falls back to the menu.

**Why the header.** One action per key covers what players expect from a game's keys without a key-binding language; full rebinding can come later as a player setting.

### D-064 — A local project launcher reuses the editor, player and exporters (accepted, 2026-11-17)
`emaki launch` (also `npm run launch`) opens a local project manager in the browser: create/open a game, return to recent projects, open its editor or player, and export Web or Desktop. `emaki edit <game>` and `emaki play <game>` also work directly. The existing commands and environment variables continue to work.

The launcher is part of the CLI (`src/launcher.ts`, browser UI in `launcher/`), with no new UI dependencies. It runs the real editor/player as Vite servers, reuses one session per game and mode, and closes them on shutdown. The editor's configuration is shared with its existing Vite entry point. Exports run the existing CLI in a child Node process: its build environment cannot change that of the running editor or launcher, and output/errors are shown in the launcher.

Game folders stay independent of the engine. Only recent paths and timestamps are stored in `~/.emaki/launcher.json` (override with `EMAKI_LAUNCHER_STATE`); removing a recent project never deletes its files. Moved projects stay visible as missing. The folder browser is provided by the local backend, since a browser cannot supply arbitrary local directory paths through a native picker. All launcher APIs bind to 127.0.0.1 and reject cross-origin requests, including filesystem reads. A packaged application with native dialogs can reuse this interface later; this version still needs the repository and Node installed.

### D-065 — One editor, three workspaces; panels follow one position and edit one line (accepted, 2026-11-18)
The editor showed the script, the game and a flowchart side by side. Writers asked for what game engines' editors give: a place to stage a scene and a place to plan routes, without leaving the script behind.

**Decision.** The editor has three workspaces over the same panes: Write (script and game), Stage (game, inspector and the scene's lines as a timeline) and Story (flowchart). Switching only changes the layout, so the game keeps running and nothing reloads. Every panel follows one position, the file, scene and line under the cursor, and shows what it knows about it.

The inspector and the stage edit **one line**: the statement on the cursor's line is parsed on its own, changed, printed with the printer's statement printer and put back in place of that line. The rest of the file is never reprinted, so a writer's own layout survives, and the change is an ordinary undoable edit. Structural edits that move scenes (flowchart, asset drops) still print the whole file (D-026).

**Speed is part of the design.** Long games (D-059 to D-061) must not get slower: nothing new runs on each keystroke. The inspector parses one line when the cursor moves; the timeline is rebuilt from the analysis the script pane already makes, after typing pauses, and draws only the columns in view. Searching routes runs the real runner in a worker, with a time budget, so the page never waits for it.

**Amended 2026-11-18 (second pass).** The workspaces now share one layout, as designed: the scenes and the routes on the left, the inspector on the right, the scene's lines along the bottom, and only the middle changes (script and game, the stage, or the flowchart left to right). A route to an ending is chosen once for the whole editor: every "play from here" starts with that route's variables at the line, found by playing the scene from the route's values with the route's choices (the real runner, a scene at a time, cached per scene, route and compile). The route search records the values each variable has as every scene begins, which the flowchart colours by and the scene card shows. It runs when the editor opens and while Story is shown, not after every edit, so writing doesn't share the computer with it.

### D-066 — Plugins can change listed variables, keep their own data, and are typed (accepted, 2026-11-19)
Plugins (D-055) could change the story only through a waiting command's result. They had nowhere to keep their own data, and plugin authors had no types. Studios writing a battle system, a shop or a minigame with records would hit all three.

**Changing variables.** plugin.json lists the variables a plugin may change (`"sets": ["hp", "gold"]`), and the plugin calls `ctx.set(name, value)`. Declaring them keeps the story checkable: the compiler checks they exist and reports on the plugin.json, and anyone reading the manifest sees what the plugin can touch. The value must have the type the variable started with.

A change belongs to the line the story shows when it's made. `Runner.assign` writes it to the state and to that line's rollback entry. So going back to the line keeps the change, and going back before it undoes it, the same as a `set` before the line. Screen buttons that `set` now go through `assign` too and behave the same way; before, going back and then forward again could lose such a change.

Three things run again whenever the player redraws, so they must not change the story: redoing lasting commands after a load or rollback, plugin functions, and drawing elements. There `ctx.set` is ignored with a warning rather than thrown, because the plugin can't tell when it's being called that way.

**Own data.** `ctx.storage` is a per-plugin JSON object in the device's storage, under the game's key. It's kept across saves and playthroughs and isn't undone by rollback. Data that should go back with rollback, or that the story should see, belongs in a variable, which keeps the two kinds apart.

**Types.** The plugin API is a standalone `plugin-api.d.ts` with no imports, which the player's own code also uses. `emaki plugin <game> <name> [--ts]` starts a plugin and copies the types to `plugins/emaki-plugin.d.ts`; the dev server, editor and builds keep that copy current. A copy in the game, rather than an npm package, works for games anywhere on disk and needs nothing installed. Arguments are typed loosely (`any` by name), because the compiler has already checked them against the manifest, so TypeScript plugins can state their own argument types.

### D-067 — Windows games export with a WebView2 player and an encrypted pack (accepted, 2026-11-19)
An Electron export carries its own Chromium: Gullwing came to 313 MB, nearly all of it the browser, and every patch ships it again. Windows 10 and 11 already have a browser engine that games can use, kept up to date by Windows: WebView2.

**Decision.** `export desktop` for Windows x64, built on Windows, makes a WebView2 player: a small .NET Framework program (built by the C# compiler Windows includes) with Microsoft's WebView2 libraries and the game in one `game.emaki` pack. Gullwing comes to 4.7 MB. Games with a `steam_app_id` stay on Electron, because Steamworks and the overlay need it, and so do macOS, Linux, Windows on ARM and builds for another system. `--shell electron|webview2` overrides the choice.

**Same behaviour as Electron.** The player gives the page the same `emakiHost` (quit, full screen, achievements kept in the game) and acts the same: the window in the game's shape (1280×720 for 16:9, 960×720 for 4:3, inside the window, in display-independent pixels), size and full screen remembered, per-monitor display scaling, one copy at a time, links opened in the browser, no zoom, no browser keys or menus. On first launch it copies an earlier Electron release's storage into a fresh profile and imports the saves, so players lose nothing when a game switches.

**The pack.** Each file is split into 256 KiB chunks, each sealed with AES-256-CBC and an HMAC-SHA256 over its position, IV and ciphertext; the file index is sealed the same way. The keys are new for each build and live in the executable. The player checks each chunk before decrypting it and serves byte ranges, so movies and music seek. This keeps the game's files from being browsed or swapped, and stops casual copying. It can't stop someone who controls the computer: the key is in the program they run. The player also clears the `WEBVIEW2_*` environment variables, which would otherwise open a debugging port onto the decrypted game.

**What ships is checked.** The WebView2 DLLs go to every player, so the exporter uses one pinned SDK version: the NuGet download must match its published SHA-512, every source (download, NuGet cache or `EMAKI_WEBVIEW2_SDK`) must have that version in the DLLs, and Microsoft's license goes with them.

**Costs.** Two desktop shells to keep alike; the shared interface is small (`emakiHost`) and a smoke test plays, saves, reloads and checks the shipped executable in CI. WebView2 updates under a shipped game, where Electron pins its engine; the player uses only ordinary web features. A few Windows 10 machines lack the runtime, and the player offers Microsoft's installer.

### D-068 — Emaki Studio: the launcher as a desktop app, beside the browser tools (accepted, 2026-11-20)
Every tool needed Node 22.18 and git, then a terminal: most writers stop there. The launcher (D-064) already gathers projects, the editor, the player and exports behind one page served by Node, and Electron is Chromium with Node built in (Electron 45 has Node 24, which strips TypeScript like the CLI's Node does, so the engine's sources run unchanged).

**Decision.** `packages/studio` is an Electron app that starts the launcher in its own main process and shows it in a window. Nothing about the browser tools changes: `npm run launch`, `dev`, `edit` and the CLI run as before, and the Studio imports `startLauncher` from `@emaki/cli`, so fixes reach both. The launcher page gains only what a tab can't do, through a small bridge (`window.emakiStudio`, launcher window only): the system's folder picker in place of the folder browser. Its wording speaks of windows instead of tabs when the bridge is there.

**Windows and pages.** Editors and players open in windows of their own (the launcher's `window.open` is allowed for the loopback address only). Any other address is refused in the window and, for web and mail links, opened in the system's browser. Pages are sandboxed, with context isolation and no Node; the folder picker answers only the launcher window's own page; pages may ask only for full screen and the clipboard. One Studio runs at a time. Closing the launcher window closes the Studio and stops its servers, previews and exports (asking first when other windows are open).

**Exports** run the CLI in a child process as before, with `process.execPath`, which in the Studio is the app: `ELECTRON_RUN_AS_NODE` makes it plain Node for that child (plain Node ignores the variable). Exporting from the Studio showed a bug the browser launcher shared: the editor's and player's dev servers watched the game's `export` folder, which on Windows keeps its folders open, so a second export while the game was open failed with EPERM. They no longer watch it.

**Ports.** The Studio's launcher uses 5185 (the browser launcher 5175), so both can run at once; they share `~/.emaki/launcher.json`, so recent projects match. Sessions keep their ports (5173/5174, the next free one if taken).

**Packaged (Windows, same day).** `npm run build:studio` stages the engine as it runs from the repository: its packages (no tests), the example game, and every package they import at run time, found the way Node finds them and copied from node_modules (Vite included, which the tools use but only the root declares; only Electron's package.json, since Electron exports read its version and download the Electron they package). @electron/packager adds Electron without an asar archive (Vite, esbuild and the exporters use these as plain files), and electron-builder makes an NSIS installer for the current user (the folder can be chosen; one not ending in the app's folder name gets it added, so an uninstall removes only that), so the install folder stays writable. Installers copy files and can't carry npm's links between the engine's packages, which the engine needs (its packages import each other by name and find their files where they really are), so an installed Studio makes them when it starts: junctions on Windows, which need no administrator rights (src/link.ts). Not signed, so SmartScreen warns on the first run. About 135 MB.

**Not yet.** macOS and Linux packages, updates (they need releases on a public page), signing, and an engine version recorded in each game. A browser-only playground (no install at all) would need the editor's Vite-only modules behind a file-system layer, and waits until the app is out.

### D-069 — Which way up: `orientation:` for the player and phone apps (accepted, 2026-11-20)
Phone exports turned with the phone, so an upright phone showed a game drawn on a fixed canvas as a small letterboxed strip (D-018, amended), and nothing let an author keep an app sideways.

**Decision.** The header `orientation:` is `landscape`, `portrait` or `any`. Without it, a game with a `canvas:` is `landscape` and any other game `any`, so games without a canvas keep the portrait layout on upright phones as before. The web player letterboxes a `landscape` game at its own aspect in any host (a browser can't turn the screen). Phone exports write it into the native projects on every export: `android:screenOrientation` on the main activity (`sensorLandscape` / `sensorPortrait`, so both ways round work; nothing for `any`), and the supported orientations in Info.plist on iOS, with `UIRequiresFullScreen` for iPad when it can't turn every way (App Store requirement). Writing on every export makes the header the one place to change it; the rest of the generated projects is still left alone. `portrait` only fixes how the app turns: the game is still drawn wide and uses the portrait layout, as on any tall screen.

**Checked** on a real export: the Android project Capacitor generated for a landscape game has `android:screenOrientation="sensorLandscape"` on its main activity. The APK itself wasn't built (Capacitor 8 compiles with Java 21; the machine had 17), so the export now checks for Java 21 (JAVA_HOME, Android Studio's own, then the PATH) and says what to install instead of failing inside Gradle. It also runs Gradle's wrapper by its full path, since Windows can be set not to run programs from the current folder. iOS can only be built on a Mac, so its Info.plist rewrite is covered by tests on Capacitor's template.

### D-070 — Smaller exports: WebP, Opus and H.264, chosen per game (accepted, 2026-11-21)
Exports copied assets/ as it was, and games are often made with lossless pictures and high-bitrate sound and movies that players can't tell from much smaller files. A 1.9 GB visual novel demo shipped 870 MB of PNG, 596 MB of Ogg Vorbis and 416 MB of MP4.

**Decision.** The export can convert three kinds, each chosen on its own: pictures (PNG, BMP) to WebP, lossless or at a quality; sound (WAV, FLAC, AIFF, Ogg, MP3) to Opus at a bitrate for stereo files (mono files get half: one setting suits music and voices); movies to H.264 MP4 at a CRF. Every kind is off unless the game turns it on, so no export changes by itself. The settings live in the game folder's `export.json` (`{"compress": {...}}`), which the launcher writes from its Export card and the command reads, so both build the same thing; `--images`, `--audio` and `--video` override it for one export. A JSON file rather than story header keys: the launcher writes it while the editor may have the story open, and it describes the build, not the story.

**Only the export changes.** Conversion runs on the finished web build, before the desktop and phone exporters wrap it, so every target gets it. A converted file that is less than 5% smaller is dropped and the original kept (small UI pictures often grow as WebP); lossy sound already at or under 1.2× the target bitrate isn't encoded again; animated PNGs, pictures too big for WebP and WebM movies (which may carry transparency) are left alone. Transparency in pictures is always kept exact (`alphaQuality` 100), so sprite edges don't fringe at any quality.

**Names.** A file that changes format gets a new name, and rather than rewriting every path in the compiled story (images, voices built from `voice:` templates, screens, translations' localized assets, plugins), the build's game.json lists the renames and the player's single `asset()` looks each path up. Sound converts into `.ogg`, so Ogg Vorbis files keep their names.

**Tools.** Pictures use sharp (libvips), a dependency of the CLI with prebuilt binaries. Sound and movies need ffmpeg and ffprobe on the PATH (or `FFMPEG_PATH`): shipping ffmpeg would add tens of megabytes to the Studio and bring its GPL x264 into the app's licence, and many writers already have it. Without it those kinds are skipped with a reason, and the launcher says so beside them. Results are cached in `export/.compress-cache` by path, size, modification time and setting, so the next export converts only what changed.

**Checked** on that demo with pictures at 90, sound at 96 kbit/s and movies at CRF 23: 870 → 115 MB, 596 → 348 MB and 416 → 261 MB, 1.88 GB → 724 MB, in 12 minutes the first time and 1 minute with the cache (16 threads). 400 small pictures and 8 sound files stayed as they were. The web build played from its title through the first scenes in Chrome with no missing files.

**Not yet.** A separate setting for voices and music, resizing pictures larger than the game's canvas, and an estimate of the savings before exporting. (All three came in D-071.)

### D-071 — Voices on their own, pictures no bigger than the screen, an estimate first, and ffmpeg in the Studio (accepted, 2026-11-21)
D-070 left three things out, and asked writers to install ffmpeg themselves.

**Voices.** Speech stays clear at bitrates that would spoil music, and voices are often most of a voiced game's sound, so `voice` is a setting of its own (16 to 256 kbit/s, used as it is, mono or not, or `audio` to go with music and sound). A voice is a file the story plays as one: `play voice` paths, the files of a voiced game's lines (`story.voices`), and `sample voice` files on screens, all read from the compiled story; plus any sound file under a folder named `voice` or `voices`, for files a story finds some other way. Telling them apart by the story rather than by mono or stereo is what makes the setting mean what it says. Without a `voice`, as in settings written before, it is `audio`: voices are converted exactly as under D-070 (stereo at the setting, mono at half), and share those cached results, so no export changes. (Half of `audio` for every voice looked compatible, but a demo's stereo voices would have dropped from 96 to 48 kbit/s.)

**Large pictures.** Pixels of a picture are pixels of the canvas (`zoom 1` is its own size), so a smaller file would be drawn smaller. Rather than rewriting placements, the export lists each shrunk picture's original size in game.json `sizes`, and the player uses that size wherever it sizes a picture by its pixels (free layers, screen pictures, slider knobs). Backgrounds and ordinary sprites are sized by the screen already. A picture is shrunk only while it still covers the screen times the setting both ways (`max(screenW·f / w, screenH·f / h)`), so panoramas and tall scenes meant to be panned keep every pixel, and shrinks under 5% are skipped as not worth the softening. The setting is a share of the screen (100 to 400%) because the same game is played on a 1080p laptop and a 4K monitor; the writer chooses. JPEG and WebP pictures are only resized, never converted; with `images` off, PNG stays PNG.

**Estimate.** The launcher shows the export's size before exporting. Files already converted (the cache) count exactly. The rest of each kind are sorted by size into bands (32 for pictures and voices, 16 for music and sound, 2 for movies), the middle file of each band is converted, and the band's others are expected to shrink in the same proportion: one ratio for a whole kind was 25% off, since small UI pictures and large backgrounds compress very differently. On the 1.9 GB demo it said 710 to 732 MB in about 10 seconds, against 724 MB exported. Picture and sound samples are written to the cache, so the time isn't lost; movies are estimated from a few seconds of their middle, since encoding a whole movie for a guess would take minutes. It runs in a worker while the Compression section is open, again after each change.

**ffmpeg in the Studio.** The Studio installer now carries ffmpeg (the 6.1.1 essentials build from gyan.dev that ffmpeg-static republishes, with libopus and libx264), downloaded by the build, checked against a pinned SHA-256 and kept in `vendor/ffmpeg` with its GPL v3 licence and build notes. It is a separate program the exporter runs, not linked into Emaki, so Emaki's own licence is unchanged; the licence file and the source commit travel with it. Only ffmpeg ships: files' codec, channels, bitrate and length are read from what `ffmpeg -i` prints, so ffprobe is no longer needed, which keeps about 30 MB out of the installer. `FFMPEG_PATH` still wins, and outside the Studio ffmpeg comes from the PATH as before.
